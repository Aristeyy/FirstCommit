# «Первый коммит» — план разработки

Трек: «Образовательные решения» → направление «Карьера и стажировки».
Формат: чат-бот MAX + подключённое к нему мини-приложение.

---

## 1. Проблема (а не «агрегатор»)

Кейс прямо просит не начинать с «сделаем агрегатор/навигатор». Поэтому формулируем через пользователя:

> **Студент 2–4 курса IT-направления** (СПО или вуз), который ищет **первую оплачиваемую стажировку**,
> хочет **успеть подать заявку в подходящую программу**, но сталкивается с тем, что **наборы разбросаны
> по десяткам карьерных сайтов компаний с разными сроками, требованиями и форматами**, из-за чего
> **пропускает дедлайны и тратит часы на ручной мониторинг**, а многие подходящие программы просто не находит.

Ключевой инсайт: у стажировок в IT есть **сезонные окна набора с дедлайнами** (в отличие от обычных вакансий).
Ценность продукта — не «список», а **«не пропусти свой набор»**: подбор под профиль + напоминания о дедлайнах.

### Что нужно подтвердить (раздел «актуальность», 25% продуктовой оценки)
- [ ] Статистика: число студентов IT-направлений (Росстат, Минобрнауки), данные о трудоустройстве выпускников.
- [ ] Разбор As Is: сколько источников студент должен мониторить вручную (посчитать реальные карьерные страницы).
- [ ] Мини-опрос 15–30 студентов (Google/Яндекс Формы): как ищут, сколько источников, пропускали ли дедлайн.
- [ ] Отделить в презентации **факты / гипотезы / допущения**.

## 2. Целевой сегмент
- **Приоритетный:** студенты 2–4 курса IT-специальностей, регион пилота — **Республика Татарстан** (финал в Казани; КФУ ИТИС, КНИТУ-КАИ, Иннополис, колледжи).
- **Вторичные (для масштабирования):** выпускники СПО, карьерные центры вузов, старшеклассники ИТ-классов.

## 3. Основной пользовательский сценарий (end-to-end)
1. Студент открывает бота → короткий онбординг кнопками (3–4 вопроса: направление, курс, город/удалёнка, стек).
2. Кнопка «Открыть подборку» → мини-приложение: список стажировок, отсортированный по соответствию профилю.
3. Умные фильтры: направление (backend/frontend/mobile/QA/data/ML/DevOps/дизайн), стек, формат (офис/гибрид/удалёнка), город, оплачиваемая, курс/год выпуска, **статус набора (открыт / скоро / закрыт) и дедлайн**.
4. Карточка стажировки: требования, сроки, этапы отбора, **источник и дата актуальности**, кнопка «Подать заявку» (ссылка на первоисточник).
5. «Отслеживать» → бот присылает напоминания: открытие набора, за 3 дня / 1 день до дедлайна, новые совпадения по профилю.
6. Результат: студент подал заявку вовремя, не мониторя 20 сайтов.

Почему такое разделение (по рекомендациям стр. 15): бот — онбординг, уведомления, короткие действия;
мини-приложение — каталог, фильтры, сравнение, возврат к сохранённому.

## 4. Метрики (гипотезы для пилота)
- Время на поиск подходящих стажировок: ~N часов → ≤10 минут.
- Доля пользователей, открывших карточку и перешедших к подаче заявки.
- Доля отслеживаемых стажировок, по которым пользователь перешёл к подаче до дедлайна.
- Retention: возвраты после уведомлений.

## 5. Архитектура

```
 Пользователь MAX
   │  чат                         │  мини-приложение (HTTPS)
   ▼                              ▼
┌────────────┐  webhook/long-poll ┌─────────────────────────┐
│  MAX Bot   │◄──────────────────►│  backend (Node/TS)      │
│  API       │                    │  ├ bot/     — сценарии  │
└────────────┘                    │  ├ api/     — REST для  │
                                  │  │           мини-аппа  │
                                  │  ├ parsers/ — сбор      │
                                  │  └ scheduler — напомин. │
                                  └──────────┬──────────────┘
                                             │
                                     ┌───────▼───────┐
                                     │  PostgreSQL   │
                                     └───────────────┘
 caddy (reverse proxy + HTTPS) → отдаёт статику miniapp и проксирует /api
```

Сервисы в `compose.yaml`: `db`, `backend`, `worker` (тот же образ, другая команда — парсеры+напоминания), `web` (Caddy + собранный miniapp).

### Стек (рекомендация кейса — JS/React)
- **Язык:** TypeScript везде (единые типы между ботом, API и фронтом).
- **Бот:** официальная библиотека MAX Bot API для JS/TS (dev.max.ru → bots-coding/library/js).
- **API:** Fastify + zod (валидация входных данных).
- **БД:** PostgreSQL 16 + Drizzle ORM (или Prisma) + миграции.
- **Парсеры:** `undici`/fetch + `cheerio`; **без headless-браузера** (Playwright/Chromium ломает лимит сборки 5 минут).
- **Мини-приложение:** React + Vite + **MAX UI** + **MAX Bridge**.
- **Инфраструктура:** Docker multi-stage, Caddy, VPS с доменом (или туннель на время разработки).

## 6. Данные и источники
Принципы из кейса (стр. 18): первоисточник, дата актуальности, не имитировать интеграции.

| Источник | Способ | Статус в MVP |
|---|---|---|
| «Работа России» (открытые данные trudvsem) | официальный открытый API | live — госисточник, сильный аргумент |
| Карьерные страницы IT-компаний (стажировки) | адаптер на каждый сайт, HTML/JSON | live для 3–5 крупных, остальное — seed |
| hh.ru | публичный API — **проверить текущие условия доступа** | по результатам проверки |
| Ручной seed-набор | `db/seed/*.json`, помечен как тестовые данные | fallback, всегда доступен |

Правила парсинга: соблюдать robots.txt и условия сайтов, низкая частота запросов, User-Agent с контактом,
кэширование. Каждая запись хранит `source_url`, `fetched_at`, `is_synthetic`.
В интерфейсе видно источник и дату обновления.

Схема данных (черновик): `internships`, `companies`, `sources`, `tags` (стек/направление),
`users` (max_user_id, профиль), `subscriptions`, `notifications_log`.
Персональные данные минимальны: id пользователя MAX + профиль без ФИО/телефона (152-ФЗ).

## 7. MVP — MoSCoW
**Must:** онбординг в боте · каталог с фильтрами и сортировкой по соответствию · карточка с источником и датой · отслеживание + напоминания о дедлайнах · 1 live-источник + seed · Docker одной командой · README.
**Should:** 3–5 live-адаптеров · «соответствие профилю» в % с объяснением · избранное · валидация initData мини-аппа на бэкенде.
**Could:** сравнение 2–3 стажировок · чек-лист подготовки к отбору · шеринг карточки другу в MAX.
**Won't (осознанно):** подача заявки внутри продукта, резюме-конструктор, LLM-чат, личный кабинет работодателя, покрытие всех сайтов РФ.

## 8. Платформенный бонус (+0,15, только целиком)
Кандидат: **уведомление в чате → deep link прямо в нужную карточку мини-приложения** + шеринг карточки в чат через MAX Bridge.
Должно работать от начала до результата и быть описано в README/презентации. Перед реализацией сверить методы в документации MAX Bridge.

## 11. Риски
- Сайты меняют вёрстку / блокируют парсер → адаптеры изолированы, есть seed-fallback.
- Сертификаты: API MAX может требовать доверенный корневой сертификат Минцифры — добавить в Docker-образ.
- HTTPS для мини-аппа нужен с первого дня — заранее домен/VPS.
- Ник бота менять нельзя — не пересоздавать бота.
- Документация MAX меняется — сверяться перед сдачей.
